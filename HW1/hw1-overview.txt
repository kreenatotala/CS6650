PART 2
1.  A Virtual Machine (VM) is a software-based emulation of a physical computer that runs an operating system and applications just 
    like a real machine, but it runs inside another computer (the host) using virtualization technology. Running a Go server locally 
    uses your laptop’s CPU and memory. Running the same server on an EC2 instance runs it in a cloud-based VM, isolated from other 
    users, and accessible globally if configured as such.

2.  If my IP changes, I would have to update he security group with the new IP or update it to 0.0.0.0/0 to allow traffic from anywhere.

3.  By default, every time an EC2 instance is stopped, restarted, or terminated, it gets a new public IP. An Elastic IP (EIP) is a static 
    IPv4 address you can allocate to your AWS account and associate with your instance. Using an EIP ensures your instance keeps the same 
    public IP even after restarts or failures. However, if you create an EIP and it is unused, it can incur a small cost.

4.  When selecting an EC2 instance type, you're essentially choosing a combination of compute capacity (vCPUs), memory (RAM), storage, 
    and networking performance tailored to your application's needs. AWS offers various instance families optimized for specific workloads.
    Understanding and selecting the appropriate instance type ensures optimal performance by atching your application's requirements with 
    the right resources. Ensures the correct tradeoff between cost efficiency and scalability.

Distribution shape: My distribution shows most response times tightly clustered between 155–165 ms, but with a noticeable long tail that 
stretches up to almost 300 ms. This means that while the majority of requests are very fast, a small percentage (less than 5%) fall into 
the slower category above about 180 ms.

Consistency: Looking at my scatter plot, response times are generally consistent around 160 ms, but there are occasional spikes into the 
200–280 ms range. These spikes happen sporadically rather than in a clear pattern, suggesting brief bursts of resource contention.

Percentiles: In my data, the median (50th percentile) response time is about 160 ms, while the 95th percentile rises to around 174 ms. 
That ~15 ms gap shows that most requests are stable with not much variability, but a small fraction of them take considerably longer, indicating 
some variability in performance.

Infrastructure Impact: Since I’m running this service in a single container on a basic EC2 instance, the variability in my response times likely 
comes from limited CPU or memory resources. Small fluctuations—like garbage collection in Go or shared CPU scheduling—can slow down a 
handful of requests, which explains the long tail in my results.

Scalability: If I scaled this to 100 concurrent users instead of running sequential requests, I’d expect my spikes to become more common and more severe. 
A single small EC2 instance could bottleneck under that load, and requests might start queueing up, driving response times higher. Adding more 
instances or moving to a larger one would likely help.

Network vs Processing: The baseline response time of ~160 ms in my distribution likely reflects a mix of server processing and network latency. 
The higher outliers—closer to 280 ms—could be caused by either temporary network delays or EC2 resource contention. The region of my EC2 
instance may also play a role. If the server is running far from where I’m testing, the added physical distance and internet routing hops 
increase latency. To separate these effects, I could log server-side request handling times to isolate processing, then compare them to 
client-side timings, and even test from different geographic regions to see how much network distance contributes.
